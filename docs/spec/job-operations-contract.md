## Durable record wire budgets

Every received durable JSON envelope must fit **1,048,576 UTF-8 bytes inclusive**
and **64 JSON container levels inclusive**. The byte budget includes whitespace.
`String.length` above the byte budget causes immediate refusal before UTF-8
allocation; bounded-length text then receives the exact UTF-8 byte check.
Multibyte characters count by bytes, including supplementary Unicode.

An iterative O(n) pre-parser scan tracks quoted strings and escapes. Only braces
and brackets outside strings contribute container nesting; the root object or
array counts as level one. Escaped quotes and backslashes preserve quoted
state. The strict parser retains grammar, duplicate-key and schema authority.

The operational budgets add no fields or schema versions. The closed V0/V1/V2
record shapes, persisted identity, explicit canonical ordering and format-bound
SHA-256 algorithm remain as specified by the
[Durable Job Record Contract](durable-job-record-contract.md).

## Fail-closed entry paths

`DurableJobRecordCodec.decode` and startup admission check received text before
strict parser entry. V1 and V2 signing admit unsigned bytes before computing a
signature and admit final canonical signed text before reporting success.
`canonicalJson`, `canonicalBytes`, `toRecord`, ordinary `publicProjection`, and
explicit V1-to-V2 migration apply the same final signed-envelope budget, even
for caller-constructed records whose integrity digests are otherwise correct.

V0 canonical output has its own inclusive envelope budget. V0-to-V1 migration
may refuse a fitting V0 envelope when V1 integrity overhead exceeds the final
signed-text budget. V1-to-V2 migration validates its source and destination.
Refusal never truncates, normalizes received text to evade a limit, silently
migrates, discards fields, repairs digests or bypasses tenant/subject/scope
authorization.

Byte and depth limit messages are constant bounded messages naming the violated
limit only. They expose no submitted text, raw payload, reference, subject,
tenant, secret or path. Limit refusal returns the existing structured codec
failure; startup admission returns `Corrupt` without any partially decoded
record. Store corruption and authorization refusal remain distinct.

## Signed retention classes and transitions

Phase 69.7 owns operational retained-lifecycle policy. The historical V1/V2
retention fields and format-bound signatures remain unchanged. `Keep` means
`expiresAt=None`; `TTL` means an explicit `expiresAt=Some(deadline)`.
`LegalHold` means `retainUntil=Some(Instant.MAX)` and takes precedence over both.
Keep prevents automatic expiry while permitting authorized explicit deletion.
No clock is inferred: each command supplies its observation time.

`Expire` changes Active to Expired only for terminal Succeeded, Failed or
Cancelled records, at or after both the expiry and any finite retention floor.
The deadlines are inclusive. Submitted, Running and Suspended return
`NotTerminal`; future deadlines return `NotDue`, Keep returns `Kept`, and a hold
returns `Held`. `Delete` changes terminal Active or Expired to Deleted with
`deletedAt=now`, only after any finite floor; a hold blocks deletion too.
Logical deletion preserves every input/result/calltree/definition reference and
all other non-retention body facts. It does not acknowledge physical cleanup.

`Hold` applies only to Active records, including active executions. It preserves
expiry while replacing the floor with `Instant.MAX`. Reapplying hold returns
`Held` without writing. `ReleaseHold` applies only to an Active held record and
requires an explicit replacement: `None` clears the floor; `Some(instant)` must
be non-null, at or after creation, and different from `Instant.MAX`. An
overwritten floor is never guessed or restored.

Expired plus Expire returns `AlreadyExpired`; Deleted plus Expire/Delete returns
`AlreadyDeleted`; Tombstoned plus Expire/Delete returns `Tombstoned`. Hold or
ReleaseHold on non-Active retention returns `InvalidTransition`. These outcomes
do not advance semantic or provider revisions.

## Authorized optimistic maintenance

Every command additionally requires caller scope `cncf.job.retention.manage`.
The exact stored tenant, submitting subject and required scopes must still
match. Full scopes, admin labels and wildcards confer no cross-subject or tenant
bypass. The manage capability is not inferred from stored authorization and is
not added to a record's `requiredScopes`.

Capability refusal precedes provider access. A supplied observed snapshot is
canonical-validated and startup-admitted with caller access, then compared with
a newly loaded authoritative record and provider revision. `Missing`, `Corrupt`,
`Refused` and `Stale` are closed no-write facets. Intact current values alone may
be re-signed. A changed body preserves its V1/V2 format, job id, creation time,
authorization, lifecycle and every non-retention value, advances semantic
revision by exactly one, and assigns `updatedAt=now`. A null or backward write
time returns `InvalidTransition`; revision `Long.MAX_VALUE` returns
`RevisionExhausted`. Signing or optimistic checkpoint failure returns only
`WriteRefused`, without raw provider messages or overwrite/repair of corrupt or
concurrent values.

Expired, Deleted and Tombstoned values remain canonically readable by authorized
maintenance. Ordinary public projection and recovery classification refuse all
three with fixed bounded messages. Active TTL values remain readable until an
explicit maintenance checkpoint expires them; consumers never consult a clock.

## Bounded caller-invoked expiry sweep

A sweep takes an explicit candidate source, caller-injected time and requested
bound in `1..1024`. Before any store effect the entire returned vector must be
non-null, fit the requested count, contain non-null candidates with nonblank
distinct job ids, and carry contiguous zero-based Long ordinals. Invalid bounds,
source failure, over-supply, duplicate ids, ordinal gaps and blank/null values
produce constant bounded failures. The source is never truncated or silently
skipped, and source admission performs no speculative candidate mutation.

Each candidate supplies its own access and receives expiry-only maintenance with
the same capability, authorization, integrity, observed-revision, terminal and
hold checks. Reports contain only ordinal and closed facet in source order,
with at most 1024 entries. They expose no record, payload/reference, credential,
provider failure, subject, tenant or path. Candidate effects are independent:
an earlier successful expiry remains persisted when a later candidate refuses.
The report is per-candidate evidence rather than a transaction across jobs.

## Exclusive Job-owned payload authority

An opaque external reference alone grants no ownership. Only
`storageKind=job-owned-blob`, issued by `DurableJobOwnedBlobPayloads`, identifies a
candidate owned payload. Ordinary/legacy opaque references, external URLs and
other storage kinds retain their own owner's lifetime. Definition
`declaredSource` is protected even when its storage kind is Job-owned; it never
becomes a Job cleanup target. A canonical Blob identity overlapping any shared
or definition position refuses the complete cleanup plan.

The producer admits a canonical signed, normally authorized, current observed
Active snapshot. Exact tenant, submitting subject and required scopes remain
mandatory; production does not require or add the retention manage capability.
The trusted runtime `IdGenerationContext` allocates a fresh canonical Blob entity
ID with purpose `durable-job-owned-payload`. There is no caller-supplied ID,
reserved-attribute injection, existing-Blob attachment, key recycling or
deduplication API. Typed `EntityStore.load[Blob]` must acknowledge absence before
`BlobStore.put`; load failure does not mean absence. The configured allocator
must guarantee unique allocation; distributed fencing remains outside this
Phase.

The adapter writes Binary payloads using the caller's filename, content type and
`BinaryBag`, with only its own reserved attributes. A put acknowledgement must
match the issued ID and configured store, have a nonnegative byte size, nonblank
content type and 64-hex SHA-256 digest. Actual Blob EntityStore metadata records
Managed mode, the exact provider-issued storage reference/content evidence, no
external URL and the CNCF content route. Publication rechecks current Active
authority. Post-put content, metadata or current-snapshot refusal attempts
idempotent rollback only when the acknowledgement proves a handle for this
newly allocated ID in the configured store. A null or foreign ID/reference/store
does not authorize deletion. Failed rollback remains failure; any created
metadata remains audit/recovery evidence. Refusal returns one fixed bounded
message without provider text or identities.

Ownership lives in immutable Blob attributes, without a Job schema addition:

- `cncf.job.payload.ownership=exclusive-v1`;
- `cncf.job.payload.owner` is lowercase SHA-256 of job ID, creation instant,
  tenant ID, submitter kind and submitter ID in that order;
- `cncf.job.payload.binding` is lowercase SHA-256 of issued Blob ID,
  `storageRef.print`, version, etag, content type header, decimal byte size and
  digest in that order.

For both hashes each present value is a tag byte `1`, four-byte big-endian UTF-8
byte length, then its UTF-8 bytes. An absent optional value is the distinct tag
byte `0`. Instants use `Instant.toString`; sizes use decimal `Long.toString`.
These hashes are equality labels over trusted authoritative provider metadata,
not cryptographic authentication or protection against a malicious provider.
The adapter never rewrites ownership after publishing a reference.

## Physical cleanup and durable tombstones

`cleanupObserved` requires `cncf.job.retention.manage` before any provider access,
then canonical validation, startup admission under unchanged ordinary
authorization, authoritative reload and complete snapshot equality. Missing,
Corrupt, Refused and Stale are closed no-effect facets. Corruption is never
re-signed or repaired by cleanup. Tombstoned returns stable AlreadyTombstoned;
Active/Expired return NotDeleted. Only terminal Deleted records may proceed;
LegalHold returns Held, nonterminal execution returns NotTerminal, a future
finite retention floor returns NotDue, null/backward time returns InvalidTime,
and exhausted semantic revision returns RevisionExhausted before physical work.
Explicitly Deleted terminal Keep is eligible.

Preflight enumerates all input External, Succeeded External result and calltree
payload positions, and counts protected declared-source evidence too. The whole
reference vector must fit 1024 inclusive; 1025 returns ResourceBoundRefused
before metadata lookup. Owned IDs must round-trip to exactly `EntityId.value`
and the Blob collection. Distinct IDs preserve first-occurrence order;
conflicting duplicate content, malformed/wrong-collection IDs and owned/shared
or definition overlaps refuse the entire plan, without truncation.

Before the first deletion, every distinct owned target must have real typed Blob
metadata with exact canonical ID, Managed mode, no external URL, exclusive
ownership and matching creation/principal fingerprint. Content type, size,
SHA-256, immutable binding and configured store must match exactly. Missing,
malformed, foreign or unavailable metadata yields OwnershipRefused with zero
physical deletions, even when earlier targets are valid. A caller path, URL or
storage handle can never be a deletion target.

Only exact preflighted provider storage references go to `BlobStore.delete`, in
deterministic order. Successful delete acknowledgement is completion authority;
a generic get failure proves nothing. Failure/NonFatal yields
PayloadDeleteRefused, preserving Deleted and every reference while keeping prior
physical successes. Fresh-provider retry uses retained immutable owner metadata
and idempotent deletion; no in-memory cleanup ledger is recovery authority.

After every target acknowledges, cleanup freshly reloads the same observed
Deleted snapshot and performs an optimistic format-preserving Tombstoned
checkpoint. Only retention and identity revision/update time change: revision
advances once, `updatedAt=now`, the original logical `deletedAt` is repeated in
the tombstone, reason is `job-owned-payload-cleanup-complete`, and replacement ID
is absent. A checkpoint race/failure returns CheckpointRefused and preserves
newer authoritative state. A later eligible retry can finalize without restoring
disposed bytes. Blob metadata and all Job body/reference evidence survive
tombstoning. Non-owned-only Deleted records may receive a zero-payload tombstone.
The tombstone certifies disposal of Job-owned bytes; it certifies neither
shared/external/definition disposal nor audit metadata erasure.

## Bounded coordinated and scheduled maintenance

`DurableJobMaintenance.sweep` takes explicit source/access, bound and observation
time. Source, null/time/bounds and the entire candidate vector are admitted
before effects, using B1's inclusive 1..1024, non-null, nonblank distinct job IDs
and contiguous zero-based ordinal rules. There is no source truncation. Each
candidate supplies access; authority is never reconstructed. Active candidates
perform due Expire, fresh-load Expired/Delete, then fresh-load Deleted/cleanup.
Existing Expired and Deleted resume at their respective stages. Keep, hold,
nonterminal and not-due Active outcomes stop that candidate; any failed stage
stops progression. Earlier candidate successes remain when later candidates
refuse. Reports contain only ordinal, at most two closed B1 retention facets and
an optional closed cleanup facet, in source order and at most the requested/1024
count. Source/time failure has one bounded failure and zero Job/Blob effects;
candidate failures/NonFatal normalize to closed facets.

`DurableJobMaintenanceScheduler` is the explicit runtime lifecycle owner around
that coordinator, with injected context, candidate source, stores,
`JobTimeSource` and `JobTimer`. Construction has no effects. Start validates
period in 1 second..24 hours inclusive and candidates in 1..1024, then registers
one future task at now+period. Repeated start is idempotent; a closed owner cannot
restart. Null/overflow clock and registration failure are bounded, visible
failures; scheduling stops after registration refusal. Timer registration is
nonblocking and must not invoke callbacks before their future due instant.

Under one monitor each registration generation is consumed once, with at most
one admitted run. Provider work executes outside that monitor. At completion,
only the bounded result is saved; an open owner rearms at completion-clock time
plus period. Failure also rearms. There is no catch-up, backlog, sleep loop,
implicit executor or global daemon. Close cancels only this owner's registration,
permits admitted work to finish, and prevents later/duplicate/stale callbacks
and rearm. It never shuts down the shared timer. Status contains only
started/closed/in-flight, next due time and the bounded last result.

Configuration must explicitly provide a real runtime lifecycle owner. B2 adds
no implicit bootstrap, public JobEngine ABI/route or catalog `available=true`
claim; an unconfigured runtime remains unavailable. JM69-09D and JM69-10 must
prove configured real runtime ownership and fresh-process behavior using this
production coordinator/owner.

## B3A runtime resource rules

### R1: finite policy and construction

The default and hard upper limits are retained Job identities **4096**, pending
work **1024**, executing work **64**, tasks in one submission **1024**, and retry
attempts **32**, all inclusive. Package-internal `JobResourcePolicy` may lower
any limit to at least one. `RetrySchedule.maxRetries` is zero through the
configured retry cap; `SchedulerConfig.workerCount` is one through the configured
execution cap. Retry delay vectors are non-null, contain at most the configured
retry cap, and contain only positive durations at most 24 hours inclusive.
Positive subsecond delays and short vectors remain compatible. Invalid policy,
worker/retry construction or preseeded oversupply refuses before executors,
timers, provider writes or task dispatch. Existing public constructors, case-class
product/copy/unapply shapes and JobEngine APIs remain unchanged.

### R2: atomic admission before effects

The actual `InMemoryJobEngine.State` owns one private budget and state monitor.
Engines sharing that State share its counters. Policy binding is package-only and
freezes at the first attachment. Async submission reserves retained plus pending;
Sync submission reserves retained plus executing. All requested components are
checked together before any Job/Task ID, record, event, timeline, native admission
or user dispatch. Busy admission returns the constant existing serviceUnavailable
Consequence, `JobEngine resource capacity unavailable`, without supplied data,
identity, provider text, credentials or paths. Normal task-admission observers
retain their established durable admission failure contract.

### R3: retained identities and opaque leases

Retained identities are the distinct union of durable/runtime maps, registered
terminal facts and committed reservations. Bounded iteration seeds this union
before engine effects; a complete seed must fit. Opaque budget-issued leases count
provisional reservations, commit identity after native admission, and release
unpublished components idempotently on refusal. Existing identity updates/retries
consume no second retained slot. Terminal settlement and shutdown preserve
retained identities; quota cleanup never deletes or overwrites admitted durable
records. Pending includes queued, reserved-to-be-enqueued and future delayed work.
Queue envelopes pair an existing SchedulerWorkItem with its exact lease and retain
priority then sequence ordering. Quota-monitor code performs only counter/lease
and private queue operations, enters no state monitor, and calls no provider,
task, event sink or state-mutating callback.

### R4: physical execution ownership

Sync roots, workers, manual drains and external Sync child calls share the
execution cap. Claim acquires execution before dequeue; busy `drainOne` returns
false without changing pending work. Workers wait interruptibly on the shared
condition for their queue and capacity, reserving no execution while empty and
using no sleeps, spins or polling. Every completion, cancellation, checkpoint
refusal, exception or interruption releases execution in finally and wakes waiters.

### R5: child admission and trusted nesting

Queued SameJob admission reserves pending before Task ID or pending-count,
read-model or timeline mutation. External Sync child admission reserves execution
before Task ID and running intent. Only the actual executor's same-thread,
same-engine, same-Job ThreadLocal stack can reuse its physical lease. Submitted
JobContext IDs and task stacks cannot confer that authority. A new Sync Job
always needs another lease. Compensation runs inside its existing root/task
lease. Busy refusal preserves the prior record/result, counters, timeline and
events. B3A does not bound cumulative lifetime task/history entries.

### R6: delayed generations

A delayed start/retry holds pending at admission. Its exact generation transfers
that lease to the priority queue at due time without a second reservation; stale,
duplicate or concurrent callbacks consume a generation at most once. Registration
follows durable admission ordering. Initial registration failure releases pending,
preserves the admitted identity and record, marks bounded terminal scheduling
failure with existing checkpoint ordering, and still returns the admitted JobId.

### R7: retry exhaustion and original failures

Control Retry reserves pending before changing Failed/Cancelled status, result,
retry evidence, timeline, events or cancellation scope; busy refusal preserves all
of them. Automatic Immediate/Delayed retry reserves pending before increment,
reset, enqueue or schedule. Busy capacity, a missing requested delay, clock/date
overflow or registration failure yields exhausted, recoveryRequired, deadLetter,
non-poison terminal evidence with the original failure Conclusion and actual
attempt count. No replacement delay, out-of-vector access, overflow or Submitted
job without work is inferred. The existing terminal outcome checkpoint precedes
terminal publication; native checkpoint refusal remains an explicit refusal fact
and publishes no claimed durable success.

### R8: quiesce, cancel and shutdown

Quiesce refuses new submissions, control Retry and child admission while admitted
queued, delayed and executing work may finish. Cancel invalidates only this
engine's matching pending generations, removes matching queue envelopes, closes
those registrations, releases pending and decrements removed queued-child counts
before terminal settlement. Active execution releases only at physical completion.
forceCancel/shutdown clears only this owner's pending work and wakes its waiters,
retaining records and schedule/retry facts for restart. Injected shared timers
are never shut down; only engine-created timer/executor resources are shut down.
Another State owner's pending work is preserved.

### R9: complete bootstrap and recovery registration

Constructor rehydration reserves the entire eligible delayed-start/retry batch
before registering its first timer. A complete batch must fit. Shared engines
cannot register a duplicate logical root generation; owner close permits a fresh
engine to restore it. Timer failure unwinds this owner's bootstrap leases and
registrations, refuses visibly, and neither truncates records nor invokes tasks.
