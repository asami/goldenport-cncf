# GMO security incidents: Textus defense assessment

Date: 2026-11-02
Status: architecture case study; incident facts require primary-source verification

## Purpose
Assess whether Textus architecture **and standard operations** would prevent, contain, detect or recover from real incidents. Separate verified facts, hypotheses, planned controls and implemented guarantees. Never claim an incident was preventable without a demonstrated enforcement path.

## Evaluation framework
- Development: CML/model contracts, car-lint, review and admission.
- Runtime: CNCF UoW, capability, authorization, Security Complete CAR and sandbox.
- Infrastructure: isolation, signed images/CAR, immutable deployment and trust boundaries.
- Operations: active/standby rotation, monitoring, incident containment, forensic preservation and recovery.
- Data: EAI private workspace, artifact lifecycle, destination admission and controlled sharing.
For each control record implemented/planned/proposed and mandatory/default/optional, plus bypass paths and acceptance evidence.

## Case A: GMO Trust Login
Reported issue: personal/contract information and temporary files accessible in public-facing storage. The reason for placement (test residue, storage reuse, changed ACL, etc.) is **unknown**; these are hypotheses only.

Textus approach: non-entity raw data and derived files receive artifact classification and provenance; processing in private workspaces; tools cannot write directly to public destinations; EAI resolves logical retention destinations, cleans temporary artifacts and requires explicit publication admission. Time-limited sharing substitutes for ad-hoc public staging. Test: confidential CSV generated by a sandbox tool cannot reach public storage; expired grants and abandoned artifacts are reclaimed. Immutable rotation alone does not correct a bad persistent storage policy.

## Case B: Onamae desktop cloud
Reported issue: unauthorized access and suspected malicious software. Initial intrusion vector unconfirmed. CNCF approach: Security Complete CAR admission, Docker isolation for other code, restricted mounts/network/secrets, signed deployment, immutable rotation with active/standby. Rotation reduces persistence only when clean image, control plane and persistent data are protected. It does not prevent initial compromise or exfiltration before rotation. Test escape, lateral movement, malicious persistent volume, image compromise and forensic snapshot before teardown.

## Case C: GMO Research & AI / infoQ
Reported issue: unauthorized access, personal data exposure and point exchanges; precise exploit chain requires verification. CNCF authorization and business invariant enforcement plus rate/risk policy, audit, anomaly detection. Immutable rotation has limited value against valid-API abuse. Test per-tenant bulk access and repeated redemption, including idempotency and account ownership.

## Cross-project findings
1. Entity-store security does not cover CSV, logs, caches, uploads, backups and temporary files.
2. CNCF provides enforcement primitives; EAI governs artifact movement and retention; domain services retain business authorization.
3. Distinguish direct prevention from containment and recovery; classify remaining risk and operational assumptions.
4. Avoid duplicative checks: prefer constrained paths and testable admission over per-application defensive code.
