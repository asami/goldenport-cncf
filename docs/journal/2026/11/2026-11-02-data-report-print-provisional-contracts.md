# データ供給・帳票生成・印刷依頼／結果の仮仕様

Date: 2026-11-02
Status: Provisional / Development Candidate
実装・検証: 未実施

## 位置付け

OLAP／BIと業務帳票は専門家に任せるための土台までをTextus／CNCFが提供する。この責任分界を、データ供給、帳票生成、印刷依頼・結果の3契約として仮整理した。備忘録用の[開発候補計画](../../../notes/data-report-print-foundation-development-plan.md)と対応する。

本記録は仮仕様であり、既存の規範仕様・公開API・実装済み機能を変更しない。具体的な型名、操作名、保存方式、コンポーネント名は着手時に確定する。

## 1. データ供給契約

対応候補: DVL-DATA-REPORT-PRINT-01

### 目的

専門家が定義した分析モデルや帳票へ、意味・型・識別子・関連を保った業務データを渡す。View Model、公開Operation、Recordと既存プロバイダーを基礎にする。

### 入力と出力の仮定義

| 種別 | 内容 |
| --- | --- |
| 入力 | 公開データセットまたは公開操作の識別子、項目・条件・順序、取得範囲、対応している時点指定、要求形式 |
| 実行側の文脈 | 認証主体、企業・組織の範囲、権限、ロケール、タイムゾーン、追跡情報 |
| データ | Record等の構造化データ。項目の型、識別子、関連、単位・通貨・コード等の意味を参照できること |
| メタデータ | スキーマ版、実効取得条件、抽出時刻、適用した時点・整合性条件、件数、続きの取得情報 |
| 結果 | 完了・継続取得・失敗と理由。部分結果を返す場合は範囲と完全性を明示する |

### 契約上の論点

- 取得条件で権限やテナント範囲を拡張できない。公開操作を経由し、DBへの無制限アクセスを前提にしない。
- 機械向けデータは型を保持する。表示用のロケール整形と分離し、日時・金額を曖昧な文字列へ変換しない。
- 複数ページの取得中に更新が発生した場合の整合性を宣言する。スナップショット、固定境界、更新を許す取得など、実際に保証する方式を示す。
- 業務上の発生日、有効期間、記録・更新日時を区別する。SimpleEntityのupdatedAtやrevisionから過去状態を自動的に復元できるとは扱わない。
- 差分取得は、対応する場合に限り、追加・更新・削除、チェックポイント、再取得、重複の扱いを定義する。単純な更新日時だけを完全な差分保証にしない。
- 取得量・実行時間等を制限し、必要に応じてJobによる非同期処理へ接続する。
- バックグラウンド実行や成果物の受渡しでも、実効主体と必要な権限を確認する。

### 受入れ例

権限の異なる二人が同じデータセットを取得し、それぞれの公開範囲が守られる。取得途中の更新に対して宣言済みの整合性が保たれる。未対応の過去時点指定は明示的に拒否される。対応する差分経路では削除と再取得の扱いが確認できる。

## 2. 帳票生成の接続契約

対応候補: DVL-DATA-REPORT-PRINT-02

### 目的

専門家が作成した帳票テンプレート・帳票エンジンへ業務データを渡し、生成物と業務上の対象を関連付ける。レイアウト、フォント、改ページ、専門的な出力設定は帳票側が担当する。

### 入力と出力の仮定義

| 種別 | 内容 |
| --- | --- |
| 入力 | 帳票種別、テンプレート識別子・版、取得済みデータまたは許可されたデータ参照、出力形式、ロケール・タイムゾーン、対応する出力オプション |
| 実行 | 要求の識別、対象業務・主体・データ時点の関連付け、同期／非同期実行、外部プロバイダー呼出し |
| 出力 | 生成物への保護された参照、MIME型、サイズ、テンプレート版、データ時点、生成日時、利用可能なページ数等 |
| 結果 | 受付、生成中、生成完了、失敗、結果不明など。既存実行状態へ対応付け、生成完了と業務上の発行を区別する |

### 契約上の論点

- ヘッダー・明細などの構造を、帳票側が安定して利用できる形で渡す。
- 生成、保存、閲覧、ダウンロード、外部送付の権限を区別する。
- 外部帳票サービスへ渡すデータと送付先を限定する。生データ・文書本体・資格情報を診断ログへ載せない。
- 原本の再出力、保存データからの再生成、最新データからの新規生成を区別する。
- 同じ版・データによる意味上の再現と、同一バイト列の再現を区別する。同一文書の再印刷には保存済み生成物を利用する方式を検討する。
- 保管期間・削除・再発行の業務規則はアプリケーション側と決める。
- Document Componentのtechnical guide提供と、業務帳票エンジンの責務は分ける。

### 受入れ例

業務データが後から更新されても、発行時の生成物とテンプレート版を追跡できる。指定ロケールが帳票側へ渡る。権限のない利用者は生成物を取得できない。生成成功を印刷済み・発行済みと扱わない。

## 3. 印刷依頼・結果の契約

対応候補: DVL-DATA-REPORT-PRINT-03

### 目的

生成済み文書を、許可された印刷サービスまたは印刷エージェントへ渡す。プリンタードライバー、スプーラー、実機制御は専門の印刷システムへ委ねる。

### 入力と出力の仮定義

| 種別 | 内容 |
| --- | --- |
| 入力 | 文書参照、許可された印刷先の論理識別子、部数、用紙・両面・給紙等の対応する選択肢、依頼識別子 |
| 出力 | Textus側の依頼識別、印刷先側の受付識別、確認可能な状態、状態の観測時刻、失敗・不明理由 |
| 操作候補 | 依頼、状態照会、対応する場合の取消し、明示的な再印刷 |
| 記録 | 対象文書、依頼主体、印刷先、部数、依頼・受付・観測結果、元依頼と再印刷の関係 |

### 状態と再実行

- Textus側の依頼受付、印刷システムへの送信、印刷キュー受理、処理中、物理的完了を区別する。
- 物理的完了を確認できる機器・サービスだけが、その事実を結果として返す。確認できるのがキュー受理までなら、その範囲を明示する。
- 応答断・タイムアウトは、未印刷の証明にならない。結果不明として照会・照合へ進め、無条件で再送しない。
- 対応するプロバイダーでは依頼識別子による重複抑制を利用する。非対応の印刷先でexactly-onceを保証しない。
- 取消し要求と取消し確認を区別する。送信済み・一部印刷済みの場合の限界を返す。
- 再印刷は新しい明示的な操作とし、元依頼と関連付ける。通信再試行と業務上の再印刷を混同しない。

### 権限と出力条件

文書へのアクセス権と印刷の実行権を確認し、印刷先を許可済みの論理識別子に限定する。実行先の対応する用紙・部数・両面等を確認し、未対応の重要条件を黙って置き換えない。認証印刷や現場での受取り確認が必要な用途は、印刷システムとの追加の責任分界を定める。

### 受入れ例

応答断後に受付済みの印刷依頼を重複送信しない。キュー受付しか取得できないプロバイダーでは物理完了と表示しない。取消し未確認や一部印刷を正しく返す。明示的な再印刷には新しい依頼と元依頼への参照を残す。

## 共通の実装境界

- CNCF: 公開契約、実行コンテキスト、権限と共通実行・記録への接続。
- コンポーネント／プロバイダー: データ供給先・帳票エンジン・印刷サービスとの具体的な接続。
- 業務アプリケーション／専門家: 指標・分析モデル、帳票様式、発行・再発行の業務規則、印刷運用。

既存のRecord Export、Job、Workflow、Provider、Blob、監査を調査して再利用する。分析専用の履歴保存、CDC、帳票専用の永続管理、印刷エージェントを新設するかどうかは未決定とする。
