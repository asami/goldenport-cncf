# 中小企業向け業務システム基盤としてのTextus／CNCFの充足範囲と検討項目

Date: 2026-11-02
Status: 考察・開発候補（実装状況の網羅的監査・開発着手の決定ではない）

## 背景と評価

Textus／CNCFおよびTextusの基盤コンポーネント群は、中小企業向け業務システム基盤として、構想上かなり広い範囲を押さえている。モデル、トランザクション、ワークフロー、セキュリティ、国際化、外部連携、AI・知識処理、評価・運用がつながっている点に強みがある。

利用者からは、この構成に抜けがないかという問題提起があり、OLAP／BIはすでに意識している領域として挙げられた。本記録では、既存の構想と一部の仕様を参照し、実務で使い切るために対応範囲を確認・具体化したい領域を整理する。

以下の項目は未実装と断定するものではない。機構の存在、業務アプリケーションでの標準的な利用経路、導入・運用手順の整備を分けて確認する。

## 点検する領域

| 領域 | 確認・具体化したい内容 | 既存の仕組みとの接続 |
| --- | --- | --- |
| OLAP／BI | 専門家が分析を設計できるよう、意味・型・履歴を伴う業務データ、権限制御された取得・供給経路を提供する | Entity／Information／View Modelと外部分析基盤の接続。分析モデル・指標・ダッシュボードの設計は専門家が担う |
| 業務帳票 | 専門家が帳票を設計・実装できるよう、帳票用データ、出力処理との接続、権限・ロケール・発行処理との連携点を提供する | 既存のデータ・出力機構と専門の帳票ツールを接続する。個別帳票の様式・レイアウト・印刷設計は専門家が担う |
| データ移行・一括操作 | Excel取込、項目対応、事前検査、エラー行の修正、再実行、重複・部分失敗への対応 | Record Import／ExportとEAIを土台に、導入担当者が扱える操作へまとめる |
| バックアップ・復旧・更新 | DBと添付ファイルの整合した復旧、誤操作前への復元、スキーマ変更、更新失敗時の戻し方 | HA・環境交換と、業務データの復旧を分けて具体化する |
| 組織と人間の業務 | 部署・役職、兼務、代理承認、担当変更、不在時の引継ぎ、期限・督促 | User Account、Workflow、Notificationの組合せと業務固有の規則 |
| マスターと時間 | コード体系、採番、有効期間、予約変更、営業日、締め日、金額・端数処理 | モデル、組み込みデータ型、業務規則として初期設計に組み込む |
| 導入・日常運用 | 初期設定、設定診断、容量・費用の把握、障害通知、問い合わせ時の情報収集 | Control Centerなどを少人数で運用できる手順と構成へまとめる |

## OLAP／BI・業務帳票の責任分界

追記・方針の具体化（2026-11-02）: OLAP／BIと業務帳票は、専門家に設計・実装を任せるための土台までをTextus／CNCFの提供範囲とする。先の「分析用モデルを生成する」という案は、専門家が定義する分析モデルへ業務データを接続する土台として整理し直す。

### OLAP／BI

Textus／CNCFは、業務データの意味・型・識別子・関連・履歴を扱い、専門家が必要なデータを取得・供給できる経路を用意する。権限と企業・組織のデータ境界、更新方式・鮮度、業務処理への負荷を、この接続の検討項目とする。

集計粒度、指標、分析軸、ファクト・ディメンション、分析用モデル、ダッシュボードは、業務側と分析の専門家が設計する。例えば部門別売上を現在の所属で集計するか、売上発生時点の所属で集計するかは、その設計上の判断となる。基盤では、こうした判断に必要な履歴・時点情報を初期設計から扱えることが重要になる。

検討方向は、**業務モデルの意味を保持したデータ供給契約を用意し、専門家が構築するOLAP／BIへ接続する**ことである。具体的な形式、API、更新方式、担当コンポーネントは今後確認・設計する。

ファクト・ディメンション、集計粒度、変更履歴の論点は、Microsoftの[分析モデル設計資料](https://learn.microsoft.com/power-bi/guidance/star-schema)を参照する。

### 業務帳票

Textus／CNCFは、帳票で利用するデータを取得・整形して出力処理へ渡す経路と、権限・ロケール・業務処理との連携点を用意する。専門家が帳票ツールやテンプレートを使って実装できる接続を目指す。

個別の見積書・請求書・納品書などの項目構成、様式、レイアウト、印刷設計は、業務側と帳票の専門家が担当する。発行履歴・再発行などは、業務アプリケーションが必要とする契約を決め、基盤の共通機構へ接続する範囲を整理する。

Document Componentによるtechnical guideの提供と、業務帳票の制作・出力は別の責務として扱う。帳票基盤の実装先や特定の帳票製品は本記録では決めない。

## HAと業務データの復旧

既存の[Durable Job Backup and Restore Contract](../../../spec/durable-job-backup-restore-contract.md)には、native SQLiteとLocalBlobStoreを対象にしたオフラインのバックアップ・復旧契約がある。今回確認した記述は、この限定された経路に関するものであり、全アプリケーション・全データプロバイダーの復旧を確認したものではない。

業務システムとしては、DB、添付ファイル、処理状態の整合性をどの単位で復元するかを明確にする必要がある。誤更新・削除への対応、復旧時間と許容するデータ損失、復旧後の外部システムとの照合も検討対象となる。

PostgreSQLを採用する構成では、[継続アーカイブと時点復旧](https://www.postgresql.org/docs/current/continuous-archiving.html)などの既存機能を利用する選択肢がある。DBの復元と、Blob・外部への処理結果・進行中の業務の整合を合わせて設計する。

## 最初からモデルと実行基盤に組み込みたい項目

国際化では、SimpleEntityや組み込みデータ型によるモデル生成と、利用者ごとのロケールを引き継ぐ実行コンテキストを通じて、通常の開発経路から対応を得る方針を議論している。同様に、後からの変更が広範囲へ及ぶ項目を早期に明確にしたい。

1. 分析に必要な履歴・時点情報
2. 組織・企業ごとのデータ境界。複数企業で共用する場合のテナント分離
3. マスターの有効期間と業務日付
4. 業務データ・添付ファイル・処理状態の復旧単位

これらは必ずしもCNCF本体に全機能を実装するという意味ではない。モデルと共通契約で保持する情報、基盤コンポーネントが提供する機能、プロバイダーや運用構成が担当する機能を分ける。

## 次の検討の優先順位

まず、**OLAP／BI・業務帳票の専門家向け接続基盤、移行・一括操作、復旧・更新**について、既存機能と必要な標準利用経路を対応付ける。OLAP／BIと業務帳票は、専門家が担当する設計・実装へ引き渡せる土台を確認対象とする。その上で、組織・承認・マスター管理を再利用可能な部品として整理する。

目標は、技術機構の充実を、少ない個別開発で実務システムを構築・運用できる形につなげることである。各候補について、対応済み、構成・手順の整備で対応できるもの、追加開発が必要なものを区別し、担当コンポーネントと受入れ例を具体化する。Phaseへの割当てや実装は本記録では行わない。
